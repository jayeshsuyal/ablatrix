# Backend consolidation and offline retrieval audit

The completed revision 2 standalone validation consumed `epqa-dev-535` and `epqa-dev-587`. The app previously selected fresh cases only from its own `loop_documents` rows. A shared SQLite reservation table now includes external rounds. App startup imports the saved revision 2 packet idempotently, verifies its case IDs, products, questions, and corpus version, and reserves both products before any new app validation can select cases. The standalone revision 2 runner also reserves its selected cases before dispatch. The app overview and export expose reservation metadata, and the live banner counts products consumed across both paths. The first official round plus revision 2 used four of six validation products; two remain untouched. The local database was backfilled without a model call.

The live app now calls the provider's snippet-ID answer path when available. It turns selected IDs into literal stored quotes and removes validated ID markers from the shopper answer. Existing test providers can continue using the basic answer interface. Live development batches and paired validations stop further dispatch after a failed answer. A failure leaves already reserved validation cases consumed. The provider ledger records a safe error code and app run ID for a failed call; the app run error includes the attempt ID. Raw provider errors and output remain private. The ledger is a planning allowance, not actual billed cost.

`npm run feedback:retrieval-audit` runs the pinned local BGE model with network access disabled, compares BM25, dense, and hybrid rankings under the same five-passage and 6,000-character selection limits, and writes the full per-case IDs to [the current audit packet](evidence/retrieval-audit-2026-09-26.json). The [prior index](evidence/retrieval-audit-before-cqa-2026-09-26.json) covered 32/34 annotated passages with BM25, 33/34 with dense, and 32/34 with hybrid. The prior Native Union authenticity query ranked an answer-irrelevant echo/adapter passage first because its stored customer Q&A also contained the exact upstream question.

The revised index embeds and searches only the answer portion of customer Q&A, while returning the original complete passage for provenance and citation checks. The index digest and vector cache keys include the indexed text, so old vectors are not reused for changed CQA text. [The before/after comparison](evidence/retrieval-cqa-comparison-2026-09-26.json) shows the hybrid at 33/34 annotated passages, with no case losing annotated coverage. The Native Union query now selects all five annotated passages and drops the echo/adapter distractor. The 10-versus-12-inch inseam question changes its first passage, but both answers remain within the top five. The canvas quantity question still omits the explicit `number_of_pieces:12` attribute. All ten development cases retain at least one annotated passage. The reference set is AI-assisted and has acknowledged errors, so this is a narrow passage-selection improvement, not a measured answer-quality gain. The remaining two validation products should be used only for a frozen comparison, not retrieval tuning or infrastructure smoke tests.

The retrieval method string records the new CQA index. Historical saved live comparisons retain their original retrieved passages; any future paired answer comparison should freeze the current retrieval method for both arms and should not combine the historical outcomes into a claim about this index change. This slice passed 95 server tests, a production build, the offline audit, and a read-only smoke of the local app API. No paid model call was made.
